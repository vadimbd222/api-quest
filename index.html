Почему это важно

Почти каждый современный сайт — это клиент чужих API: виджет погоды на главной, кнопка «Войти через…», карта, онлайн-оплата, комментарии, курс валют. Уметь интегрировать API-сервисы — базовый навык фронтенд-разработчика, без которого не собирается ни один реальный проект.

  • Данные. Контент, курсы валют, погода и товары приходят на сайт из внешних сервисов.
  • Функции. Авторизация, оплата, карты и поиск реализуются через API и не пишутся с нуля.
  • Архитектура. Даже свой бэкенд для фронтендера — это просто API, и работать с ним нужно так же.

Что такое API

API (Application Programming Interface) — это контракт, по которому одна программа может попросить другую сделать что-то или отдать данные, не зная, как та устроена внутри.

Лучше всего суть API объясняет сама игровая приставка. Консоль понятия не имеет, что записано внутри картриджа: гонки это или платформер. Но и картридж, и консоль согласовали протокол подключения — форму разъёма и порядок обмена данными. Вставил картридж — играешь. Порт картриджа — это и есть API в чистом виде: устойчивый договор между двумя системами.

В веб-разработке роль консоли играет ваш сайт (клиент), а роль картриджа — внешний сервис (сервер). Ваш код не знает, на каком языке написан сервер и какая у него база данных, — он просто отправляет запрос по договорённому формату и получает ответ.

API вокруг нас

  • Виджет погоды на городском портале берёт данные из API метеослужбы.
  • Кнопка «Войти через VK» — это вызов API авторизации соцсети.
  • Онлайн-оплата на сайте — обращение к API платёжного шлюза.
  • Интерактивная карта — API картографического сервиса.
  • Курс валют в шапке сайта — API финансового агрегатора.

Клиент и сервер

Типовое веб-API работает по схеме «запрос — ответ» поверх протокола HTTP. Клиент формирует запрос, сервер обрабатывает его и возвращает ответ с данными и кодом статуса.

БРАУЗЕР
КЛИЕНТ
→ GET /api/facts ← 200 OK + JSON
API-СЕРВЕР

Запрос и ответ — это просто текстовые сообщения со строгой структурой: служебные заголовки (headers) и, при необходимости, тело (body) с данными. Фронтендер должен уметь читать обе части.

Виды API по доступу

  • Приватные — работают только внутри одной компании: между бэкендом, мобильным приложением и сайтом.
  • Партнёрские — доступны проверенным партнёрам по персональным ключам: API платёжных систем, маркетплейсов.
  • Публичные (open API) — открыты всем желающим, часто бесплатно или с лимитами: справочники, погода, энциклопедии. Именно с них начинают обучение.

В этом квесте мы работаем именно с публичными API: с ними можно экспериментировать напрямую из браузера. Полный список сервисов для практики ждёт вас в каталоге 6-й стадии.

Итог стадии

API — это не библиотека и не база данных, а договор об обмене сообщениями. Как только вы поймёте формат этого договора (HTTP-методы, URL, заголовки, тело ответа), любой новый API станет для вас просто ещё одним картриджем в коллекции.

REST и HTTP

HTTP — протокол, на котором браузер общается с серверами. REST — набор правил, как строить API поверх HTTP так, чтобы это было предсказуемо и удобно.

Анатомия URL

Каждый запрос адресуется URL. Разберём типичный адрес API по частям:

https://api.example.com/v1/facts?limit=3

https://
Протокол и гарантия шифрования. Публичные API работают только по HTTPS.
api.example.com
Домен сервера, который принимает запросы.
/v1/facts
Путь к ресурсу (endpoint). Версия v1 позволяет менять API, не ломая старых клиентов.
?limit=3
Query-параметры — настройки запроса: сколько отдать, как отфильтровать.

HTTP-методы

Метод сообщает серверу, что именно вы хотите сделать с ресурсом. Запомните пять основных:

Таблица 1. Основные HTTP-методы
МетодНазначениеИдемпотентенПример
GETПолучить данные, ничего не меняяДаGET /api/facts
POSTСоздать новый ресурсНетPOST /api/comments
PUTПолностью заменить ресурсДаPUT /api/users/42
PATCHЧастично изменить ресурсНетPATCH /api/users/42
DELETEУдалить ресурсДаDELETE /api/comments/7

Идемпотентность означает, что повторный запрос не меняет результат: сто раз отправленный DELETE удалит ресурс так же, как один. А вот сто POST-запросов создадут сто комментариев.

Коды ответов

Каждый ответ сервера несёт трёхзначный код статуса — по нему фронтенд понимает, что произошло. Первая цифра задаёт класс ответа.

Таблица 2. Коды статусов, которые встречаются чаще всего
КодЗначениеЧто делать фронтенду
200OK — успехОбработать данные из тела ответа
201Created — ресурс созданОбновить интерфейс, показать новый элемент
204No Content — успех без телаНичего не парсить
301Перемещён навсегдаБраузер перейдёт сам по новому адресу

Принципы REST

  1. Клиент — сервер. Логика разделена: фронтенд не знает о хранении данных, сервер — об отрисовке.
  2. Отсутствие состояния (stateless). Каждый запрос самодостаточен: сервер не помнит предыдущие.
  3. Ресурсы и адреса. URL — это существительные (/users/42), действия выражаются методами.
  4. Единообразие интерфейса. Одинаковые структуры ответов, стандартные коды статусов, предсказуемые названия.
  5. Кэшируемость. Ответы помечаются как кэшируемые, чтобы не гонять одни и те же данные.

Проверить себя можно на 7-й стадии: терминал покажет и метод, и статус, и тело реального ответа.

Форматы данных: JSON и XML

Чтобы клиент и сервер поняли друг друга, данные передаются в согласованном текстовом формате. Сегодня почти весь веб говорит на JSON, но XML всё ещё встречается в legacy-системах и SOAP-сервисах.

JSON — JavaScript Object Notation

JSON построен на синтаксисе самого JavaScript: объекты в фигурных скобках, массивы в квадратных, строки в двойных кавычках. Вот так выглядит типичный ответ API:

{
  "userId": 42,
  "fact": "Кошки спят около 16 часов в сутки",
  "length": 38,
  "tags": ["cats", "sleep"],
  "verified": true,
  "source": null
}

XML — старший брат

XML описывает данные вложенными тегами. Он многословнее, но имеет схемы валидации и до сих пор применяется в банковских и государственных интеграциях:

<response>
  <userId>42</userId>
  <fact>Кошки спят около 16 часов в сутки</fact>
  <verified>true</verified>
</response>

JSON в JavaScript

Два метода, которые нужно знать наизусть: JSON.parse() превращает текст в объект, JSON.stringify() — объект обратно в текст (например, для отправки на сервер).

// текст ответа → объект
const data = JSON.parse('{"fact":"Кошки мурлычут"}');
console.log(data.fact); // "Кошки мурлычут"

// объект → текст (с отступами для отладки)
const text = JSON.stringify(data, null, 2);

Метод response.json() объекта fetch делает parse за вас — мы используем его на 7-й стадии в живой лаборатории.

Ключи и токены

API нужно знать, кто к нему обращается: чтобы считать лимиты, тарифицировать использование и защищать данные. Для этого используются ключи и токены.

Три способа представиться

  • API-ключ — длинная строка вида a1b2c3…, которую сервис выдаёт после регистрации. Передаётся в заголовке или query-параметре. Подходит для серверных вызовов и учебных проектов.
  • Bearer-токен — временный пропуск, который клиент получает после входа пользователя. Передаётся в заголовке Authorization: Bearer ….
  • OAuth 2.0 — протокол делегированного доступа: пользователь разрешает сайту читать, например, свой профиль в соцсети, не отдавая пароль. Так работают кнопки «Войти через…».

Главное правило безопасности

Всё, что попадает во фронтенд, пользователь может увидеть в DevTools. Поэтому секретный ключ нельзя класть в HTML, CSS или JS — он должен жить на сервере, который делает запросы к API за клиента (сервер-прокси).

Как делать не надо

// КЛЮЧ ВИДЕН ВСЕМ — откройте исходники страницы!
const API_KEY = "sk_live_51H8xQ…";
fetch("https://api.pay.example/v1/charge?key=" + API_KEY);

Как делать правильно

// Фронтенд обращается к СВОЕМУ серверу…
const res = await fetch("/api/weather?city=moscow");

// …а сервер добавляет ключ и зовёт внешний API.
// Ключ хранится в переменной окружения, не в коде.

Лимиты запросов (rate limit)

Публичные API ограничивают частоту обращений: например, «60 запросов в час с одного IP». При превышении сервер отвечает кодом 429, а в заголовках часто сообщает, когда лимит обновится. В учебных проектах кэшируйте ответы и не запускайте запросы в цикле.

Чек-лист безопасности

  • Ключи — только в переменных окружения на сервере, никогда — в клиентском коде и в Git.
  • Для публичных данных без ключа используйте сервисы из каталога 6-й стадии.
  • Ограничивайте ключи по домену или IP, если сервис это позволяет.
  • Обрабатывайте 401/403: предлагайте пользователю войти, а не показывайте «сломанную» страницу.

Интеграция на фронтенде

Инструмент номер один для работы с API в браузере — функция fetch(). Она есть в каждом современном браузере и возвращает промис с ответом сервера.

Базовый шаблон

async function loadFact() {
  try {
    const res = await fetch('https://catfact.ninja/fact');

    // fetch НЕ бросает ошибку на 404/500 — проверяем сами
    if (!res.ok) throw new Error('HTTP ' + res.status);

    const data = await res.json();
    console.log(data.fact);

  } catch (err) {
    // сюда попадают и сетевые сбои, и наши throw
    console.error('Запрос не удался:', err.message);
  }
}

Что здесь происходит

  1. fetch(url) отправляет GET-запрос и возвращает промис.
  2. res.ok — проверяем статус: всё в диапазоне 200–299?
  3. res.json() читает тело и парсит JSON во второй промис.
  4. try/catch ловит сетевые ошибки (нет интернета, блокировка, CORS).

CORS: почему «чужой» API может не отвечать

Браузеры по умолчанию запрещают странице читать ответы с другого домена. Сервер разрешает это специальным заголовком Access-Control-Allow-Origin. Открытые API (как тот, что мы используем в демо) присылают его всегда; если сервис его не отдаёт — запрос делают через свой серверный прокси.

Состояния загрузки

Пока запрос идёт (он занимает сотни миллисекунд), интерфейс не должен «замереть». Минимальный набор состояний: загрузка (спиннер или прогресс-бар), успех (данные), ошибка (сообщение и кнопка «повторить»). Посмотрите на терминал 7-й стадии — там реализованы все три.

Живая лаборатория

Единственная страница курса, где запрос уходит по-настоящему. Кнопки ниже обращаются к открытому API catfact.ninja прямо из вашего браузера, а терминал фиксирует всё: команду, HTTP-статус, время и тело ответа.

API-TERMINAL v1.0

// Нажмите GET /fact — терминал выполнит настоящий запрос
IDLE

Что происходит при нажатии

  1. Строка команды. В лог печатается адрес, к которому обратился fetch.
  2. Статус и время. Сервер отвечает кодом (200 или 404) — рядом видно, сколько миллисекунд занял путь туда-обратно.
  3. Тело ответа. JSON подсвечивается: ключи жёлтым, строки зелёным, числа голубым — как в DevTools.

Кнопка «ВЫЗВАТЬ 404» обращается к несуществующему пути специально: fetch вернёт ответ, но res.ok будет равен false — ровно тот случай, который мы учились обрабатывать на 5-й стадии.

Код, который стоит за терминалом

const res = await fetch('https://catfact.ninja/fact');
if (!res.ok) throw new Error('HTTP ' + res.status);
const data = await res.json();
// data = { fact: "…", length: 42 }

У сервиса есть rate limit (см. 4-ю стадию): если нажимать кнопки слишком часто, однажды придёт 429 — и это тоже поучительно.

Стиль построения API: URL — существительные-ресурсы, действия — HTTP-методы, ответы — со стандартными кодами.
Идемпотентность
Свойство метода давать тот же результат при повторе: сколько ни отправляй DELETE, запись удалена одна.
JSON
JavaScript Object Notation — текстовый формат данных; стандарт де-факто для современных API.
XML
Язык разметки с вложенными тегами; живёт в SOAP и банковских интеграциях.
API-ключ
Строка-идентификатор приложения: по ней сервис считает лимиты и отличает клиентов друг от друга.
Токен (Bearer)
Временный «пропуск» после входа пользователя; передаётся в заголовке Authorization.
OAuth 2.0
Протокол делегированного доступа: сайт действует от имени пользователя, не зная его пароля.
Rate limit
Ограничение частоты запросов (например, 60 в час); при превышении сервер отвечает кодом 429.
CORS
Механизм браузера, решающий, можно ли странице читать ответы с чужого домена; разрешается заголовком Access-Control-Allow-Origin.
CRUD
Create, Read, Update, Delete — четыре базовые операции, соответствующие POST, GET, PUT/PATCH, DELETE.
SDK
Software Development Kit — готовая библиотека-обёртка над API, чтобы не писать запросы вручную.
Вебхук
«Обратный вызов»: сервис сам присылает POST-запрос на ваш URL, когда случилось событие.

О проекте

«API QUEST» — учебный проект по фронтенд-разработке на тему «Использование API-сервисов при разработке сайтов». Сайт не просто рассказывает про API — сам работает как API-клиент: лаборатория на 7-й стадии отправляет настоящие сетевые запросы.

Автор

Гарунов Вадим, группа 141-ПМо. Курс: «Фронтенд-разработка». Почта для связи: sss2905@pochta.com.

Стек технологий

  • HTML5 — семантическая разметка: header, nav, main, aside, article, figure, dl, таблицы с caption и scope.
  • CSS3 — кастомные стили поверх фреймворка: Grid, Flexbox, sticky, кастомные свойства, три контрольные точки (мобильные, ≥768px, ≥992px).
  • NES.css 2.6 — CSS-фреймворк в стиле 8-битных консолей.
  • Нативный JavaScript — хэш-роутер на 11 страниц, бургер-меню, загрузочный экран, фильтры, терминал fetch-запросов, прогресс в localStorage.
