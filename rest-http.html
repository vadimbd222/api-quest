STAGE 02

REST и HTTP

HTTP — протокол, на котором браузер общается с серверами. REST — набор правил, как строить API поверх HTTP так, чтобы это было предсказуемо и удобно.

Анатомия URL

Каждый запрос адресуется URL. Разберём типичный адрес API по частям:

https://api.example.com/v1/facts?limit=3

https://
Протокол и гарантия шифрования. Публичные API работают только по HTTPS.
api.example.com
Домен сервера, который принимает запросы.
/v1/facts
Путь к ресурсу (endpoint). Версия v1 позволяет менять API, не ломая старых клиентов.
?limit=3
Query-параметры — настройки запроса: сколько отдать, как отфильтровать.

HTTP-методы

Метод сообщает серверу, что именно вы хотите сделать с ресурсом. Запомните пять основных:

Таблица 1. Основные HTTP-методы
МетодНазначениеИдемпотентенПример
GETПолучить данные, ничего не меняяДаGET /api/facts
POSTСоздать новый ресурсНетPOST /api/comments
PUTПолностью заменить ресурсДаPUT /api/users/42
PATCHЧастично изменить ресурсНетPATCH /api/users/42
DELETEУдалить ресурсДаDELETE /api/comments/7

Идемпотентность означает, что повторный запрос не меняет результат: сто раз отправленный DELETE удалит ресурс так же, как один. А вот сто POST-запросов создадут сто комментариев.

Коды ответов

Каждый ответ сервера несёт трёхзначный код статуса — по нему фронтенд понимает, что произошло. Первая цифра задаёт класс ответа.

Таблица 2. Коды статусов, которые встречаются чаще всего
КодЗначениеЧто делать фронтенду
200OK — успехОбработать данные из тела ответа
201Created — ресурс созданОбновить интерфейс, показать новый элемент
204No Content — успех без телаНичего не парсить
301Перемещён навсегдаБраузер перейдёт сам по новому адресу
400Bad Request — ошибка в запросеПроверить параметры и валидацию формы
401Не авторизованОтправить пользователя на вход
403Доступ запрещёнПоказать сообщение о правах
404Не найденоПоказать заглушку (как наша страница 404!)
429Слишком много запросовПодождать и повторить позже
500Ошибка на сервереСообщить пользователю и залогировать

Принципы REST

  1. Клиент — сервер. Логика разделена: фронтенд не знает о хранении данных, сервер — об отрисовке.
  2. Отсутствие состояния (stateless). Каждый запрос самодостаточен: сервер не помнит предыдущие.
  3. Ресурсы и адреса. URL — это существительные (/users/42), действия выражаются методами.
  4. Единообразие интерфейса. Одинаковые структуры ответов, стандартные коды статусов, предсказуемые названия.
  5. Кэшируемость. Ответы помечаются как кэшируемые, чтобы не гонять одни и те же данные.

Проверить себя можно на 7-й стадии: терминал покажет и метод, и статус, и тело реального ответа.
