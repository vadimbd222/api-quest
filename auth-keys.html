STAGE 04

Ключи и токены

API нужно знать, кто к нему обращается: чтобы считать лимиты, тарифицировать использование и защищать данные. Для этого используются ключи и токены.

Три способа представиться

  • API-ключ — длинная строка вида a1b2c3…, которую сервис выдаёт после регистрации. Передаётся в заголовке или query-параметре. Подходит для серверных вызовов и учебных проектов.
  • Bearer-токен — временный пропуск, который клиент получает после входа пользователя. Передаётся в заголовке Authorization: Bearer ….
  • OAuth 2.0 — протокол делегированного доступа: пользователь разрешает сайту читать, например, свой профиль в соцсети, не отдавая пароль. Так работают кнопки «Войти через…».

Главное правило безопасности

Всё, что попадает во фронтенд, пользователь может увидеть в DevTools. Поэтому секретный ключ нельзя класть в HTML, CSS или JS — он должен жить на сервере, который делает запросы к API за клиента (сервер-прокси).

Как делать не надо

// КЛЮЧ ВИДЕН ВСЕМ — откройте исходники страницы!
const API_KEY = "sk_live_51H8xQ…";
fetch("https://api.pay.example/v1/charge?key=" + API_KEY);

Как делать правильно

// Фронтенд обращается к СВОЕМУ серверу…
const res = await fetch("/api/weather?city=moscow");

// …а сервер добавляет ключ и зовёт внешний API.
// Ключ хранится в переменной окружения, не в коде.

Лимиты запросов (rate limit)

Публичные API ограничивают частоту обращений: например, «60 запросов в час с одного IP». При превышении сервер отвечает кодом 429, а в заголовках часто сообщает, когда лимит обновится. В учебных проектах кэшируйте ответы и не запускайте запросы в цикле.

Чек-лист безопасности

  • Ключи — только в переменных окружения на сервере, никогда — в клиентском коде и в Git.
  • Для публичных данных без ключа используйте сервисы из каталога 6-й стадии.
  • Ограничивайте ключи по домену или IP, если сервис это позволяет.
  • Обрабатывайте 401/403: предлагайте пользователю войти, а не показывайте «сломанную» страницу.
